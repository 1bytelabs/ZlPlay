# iOS/iPadOS implementation reference — 2.8.3

## Source baseline

Continue the existing iOS project; do not replace it with a new unrelated application. The approved Android editing implementation is commit `c22beaca6c044a194a7695db649b2669cd5c8c0d` on `codex/mobile-project-authoring`. Desktop 2.8.3 and platform-specific Mac work remain independent snapshots. Fetch and compare branches before integrating; preserve local work, Xcode settings, entitlements, signing and Mac-specific changes. Do not force-update branches or move the existing `v2.8.3` tag.

Match Android Mobile's features, visual hierarchy and saved project behavior on iPad, adapting touch targets, safe areas and system pickers for iPadOS. iPhone must remain usable through a compact layout. Native Apple APIs are appropriate; Android Java views are a behavior/design reference, not directly reusable UI code. Desktop is the reference for shared file formats and features which predate the Mobile implementation. Do not assume a feature is implemented merely because a button exists.

## Interface

- Main screen: project/repertoire heading, song cards, original/play-in key, rehearsal/live mode, repertoire and settings; region-colored waveform timeline; transport; mixer below with a visible gap. Use a shorter timeline to preserve useful mixer/fader height on tablets, and large transport targets.
- Keep the cyan Mixer navigation button. Do not repeat a Mixer heading or add a second Organize tracks toolbar above the embedded mixer.
- Native-looking editor workspace: fixed lane headers, aligned horizontal timeline lanes, BPM/meter ruler, waveform and region/guide/pad items. Avoid long forms of ungrouped buttons as the main editing interface.
- Pinch zoom in the main timeline and both editors; zoom +/- and fit; a shared viewport across lanes; magnetic horseshoe icon for snapping. Snap both clips and playhead. Draw the grid beneath clips/waveforms and distinguish beats from measures.
- Quick adjustments: project summary; Editing card (regions, tracks, organize, project data), Saving card, Playback card. Use two columns on tablets and a responsive compact arrangement on phones. Original key is inside Project data, alongside title, BPM and time signature.
- Dark navy surfaces, discreet borders, purple primary actions/selection, cyan secondary accent, consistent rounded corners and Inter typography. Use labeled fields. All eligible dropdowns use the same dark surface, consistent chevron, touch-friendly rows and selected highlight/check. Confirmation buttons are actual shaped controls: purple Apply/Save/OK, dark bordered Cancel. Match the visual implementation in `StyledSpinner.java`, `PerformanceButton.java`, `ChannelEqDialog.java` and `res/values/styles.xml`; do not substitute default gray dialogs.
- General settings group language, keep-awake, restore last project/repertoire and playback-switch confirmation. Audio output, sounds and remote control have their own sections. There is no Player/Complete mode selector: importing a finished project must still allow editing. Remote is entered through its section.

## Authoring, mixer and persistence

- Create projects from selected song/audio folders; import WAV/MP3, `.zlplay`, `.rpp` and repertoire files. Preserve relative references and unknown shared settings when saving. Support creating/editing/reordering/saving repertoires and removing entries from the local repertoire history. Removing history must not delete music files.
- Restore the last project/repertoire when enabled. Without one, show an empty screen; do not insert a demo project into normal use. Missing ordinary audio should be clearly reported and should not freeze song selection or discard the current project.
- Regions: same full desktop preset IDs, order, localized names/colors and numbering, including composite names. See `res/values/region-presets.xml`, translated string arrays and `tests/mobile-region-presets.test.cjs`. Add/edit/delete regions, split/move/resize where supported, pad change markers and automatic arrangement jumps. Audit desktop automatic-region detection separately; a preset selector alone does not implement detection.
- Guide lane: reuse an imported guide, built-in Portuguese/English/Spanish male/female banks and external multi-file import; move, trim, split, duplicate, mute and delete clips with confirmation. Keep language/voice/phrase beside guide editing. Do not add a user guide-bank manager to general Sounds settings. Keep one transport playing guide with music; no independent guide Play. Avoid redundant filename labels inside guide waveforms interfering with seeking. Preserve distinctions between moving a clip and seeking the playhead. Desktop modifier shortcuts can be supported with a hardware keyboard, but all operations also need touch controls.
- Track editor: alignment/movement, trimming, split, duplicate, confirmed delete, per-clip gain/EQ and track mute/solo/volume. Saving must reopen with all edits audible. Per-clip changes must not accidentally apply to the entire channel. Region-editor guide/VS audition volumes are temporary; track-editor mixer controls follow their defined project behavior.
- Mixer: Master; fixed Click/Guide/Pad; VS; musical groups and tracks. Gain/EQ, mute, solo, pan, faders and meters. Group organization pins special channels above VS; user groups live below VS. Allow musical track reordering and group assignment without changing special-channel roles. Each view must reflect the same audio state.
- EQ: enabled/bypass, pre-fader gain slider, low-cut slider, high-cut slider starting OFF at the left and filling right as cutting increases. Four bands, each with shape selector (Bell/Peak, Low shelf, High shelf), frequency, gain and Q. Interactive graph points and controls stay synchronized; Cancel discards and Apply commits.
- Main output routing for Master/Click/Guide/Pad/VS is device-wide across songs and repertoires. Track/group routing remains per project. Do not show special tracks twice as ordinary routing entries. Available Apple/USB routes and channel counts must come from actual platform capabilities.

## Audio, click and automation semantics

- Compare `DemoMixer`, `ProjectArrangement`, `ProjectSpec`, `ProjectLoader`, `RppReader`, `ZlplayReader`, `ProjectAuthor`, `SetlistAuthor`, `MixerOrder` and desktop `app/zlplay.js`. Preserve clip offsets, gain/pan/mute, EQ, group order, guide refs, pad markers, original/target key, native-click choice and arrangement settings through a round trip.
- Use identical role detection, case-insensitive and boundary-aware, including underscores, separated number suffixes and accented variants. Shared fixture: `tests/fixtures/track-role-names.tsv`. Recognize Click/Guide special roles, never rename actual source files to enforce recognition.
- RPP: do not execute REAPER plugins or custom click generators. Prefer an unambiguous full-length matching WAV/MP3 click stem in the song folder. If unavailable/too short/ambiguous, use native click availability rather than presenting a generated click source as missing ordinary audio. Preserve original RPP; edit/save a portable project/session representation. Repeated RPP cuts should reuse compatible streaming sources, not open a reader per item. Keep bounded source/PCM/pitch caches.
- Native click default ON and accent default OFF only when no saved preference exists. Both remain user-editable and saved per song. Avoid doubling a generated click proxy with the real/native click. Pads and guide have their own bus behavior.
- Automatic jumps execute from the current playhead: preceding jumps are not prerequisites for later jumps. Rehearsal repeats without deleting automation. Live consumes an execution state, not the saved automation; switching to rehearsal rearms, and returning to live starts with rearmed automations. Show executed/remaining state clearly. Global automation OFF preserves automation data.
- Transpose all eligible musical instruments, excluding Click/Guide, with the shared pitch engine/licensing and synchronization behavior. Preserve tempo, click alignment and latency compensation; avoid callback disk I/O or allocation. Compare the platform-specific pitch bridge and desktop sources before selecting an iOS integration.
- Remote control follows `docs/CONTROLE-REMOTO.md` and the Android remote implementation, using existing QR/pinned-TLS pairing and desktop state. It controls desktop playback; it must not start local audio. Request camera/local-network permissions through Apple APIs with appropriate purpose strings. Do not assume Android or Windows drivers/network APIs exist on iOS.

Check iPad landscape, compact iPhone layouts, pinch/drag, popovers/dropdowns, keyboard dismissal and safe areas. Add screenshots from the actual app for the principal screen, quick settings, regions/guide, track editor, EQ, organization and settings. Do not call a mockup functional validation.

Use platform-appropriate security-scoped document access/bookmarks, sandbox storage, audio-session category/focus/interruption handling and lifecycle restoration. Decide background playback explicitly rather than assuming Android foreground behavior transfers unchanged. Confirm licenses and native dependency support for iOS. Physical USB routing, latency and a full live session require device tests; report simulator-only checks as such.

Keep visible version 2.8.3 for this parity baseline, with an independent increasing iOS build number. Preserve existing Bundle ID, signing team and provisioning. A distributable iOS artifact depends on Apple signing/provisioning; an unsigned IPA or simulator build is not a public installable release. Do not alter desktop artifacts or Android assets while implementing iOS. Build and test the existing Apple project first, then provide installation/TestFlight options permitted by the available signing setup.
